# 機車停車指南：資料、社群核實與初複審計畫

更新日期：2026-10-10。文件 issue：[#30](https://github.com/smvt1215/heavy-motorcycle-parking/issues/30)。

本文件記錄已確認的下一輪實作方向及 Claude 交叉審查後的修訂，**不是已上線功能說明**。本次文件提交不變更程式、資料庫或公開 API；各功能須依下列 issue 順序實作、驗證後才啟用。

## 1. 產品目標與範圍

- 主軸為機車停車指南，服務普通重型機車（白牌，`NORMAL_HEAVY`／普重）及大型重型機車（黃／紅牌，`LARGE_HEAVY`／大重）。本輪不增加輕型機車選項。
- 優先情境是目的地附近臨時找位，涵蓋雙北路邊格、公有及私營停車場。結果先回答「我的車能否停、如何進入、現在有沒有空位」，費率作為比較資訊。
- 核心流程：選車種 → 搜尋目的地 → 比較適用停車區與可信空位 → 核對入口及來源 → 外部導航。未知許可仍須主動開啟；已知不可停仍排除。
- 找位主流程、資料補齊與社群共同核實同一輪交付。社群以結構化回報與補證為主，不設討論串、動態牆或排行榜。
- 沿用 `/api/v1`、共通 zone wire schema、明確 `vehicle`、固定 `evaluation_at`、規則優先序及 `sort_version=1`。不改排名公式或游標契約。

現況與待核對項目參見[雙北政策與資料](twin-city-policy.md)、[整合驗收紀錄](integration-acceptance.md)、[既有帳號與回報功能](user-features.md)。

## 2. 官方、營運商與社群證據

### 2.1 資料補齊

1. 新北路邊：檢查完整分頁，查證真實收費一般機車格、分類、限制、時段，以及 `parkingstatus`／`cellstatus` 官方字典。
2. 臺北路邊：核對 XML 車種、收費機車格政策範圍、費率單位與限制，證據充分後接入匯入流程。
3. 新北路外：逐一核對16個未匹配公有場站，記錄來源 ID、名稱、行政區、地址及未匹配原因；提供可重跑核對報告。
4. 營運商：納入營運商網站、場站公告及可核對的告示照片。公開資料調查不主動聯絡外部單位，不建立泛用爬蟲。

公有轄管及政策範圍仍須官方證據。營運商明確公告可確認自身場站事實，不能用營運商或社群資料推定公有政策適用。無可靠定義時交付缺口報告，維持 `UNKNOWN`／`NULL`。

### 2.2 來源核實與事實正規化

- 新來源由管理員先核實來源身分、與場站的關係、可確認的事實類型與適用區域，保存來源 URL、證據、核實時間及配置版本。營運商網站須能由官方或已核實營運商連結追溯其身分與場站；只有名稱相似不算完成核實。
- 系統自動確認只使用已核實來源、已實作解析器及明確範圍。新 URL、任意告示照片、未知格式先轉人工；人工採納案件不會自動把該格式加入解析器。
- OCR／AI僅提供候選內容。首版不新增外部 AI 服務；沒有可靠解析規則的非結構化證據由人工複審。
- 許可、費率、空位及入口分別保留 provenance、證據時間與有效區間。官方或營運商公告不能充當即時空位來源。
- 案件採納只確認證據及提議，新增停車事實必須經來源專屬的正規化流程。規則的區域／全場層級、BASELINE／EXCEPTION、authority priority 由來源及適用政策配置決定，審查人不能任意提高層級或權威。
- 寫入前解析並預覽兩車種與相關區域的結果。不得複製未有證據的另一車種值來消除 NULL；會造成非預期覆蓋或同層 NULL 衝突時停止自動發布，交人工釐清。人工也不能繞過既有最高層衝突為 `UNKNOWN` 的解析規則。
- 更新既有同來源規則時，證據未明列的車種欄位保留原值，原值為 NULL 的仍為 NULL；新增來源規則不能借用其他來源的值填滿欄位。
- 重複引用既有正規化事實只增加證據關聯，不新增同內容規則列。來源撤回、範圍變更與對應失效，依既有版本化流程結束區間，保留歷史及首次範圍證據時間。

## 3. 系統擷取照片拍攝時間

### 3.1 擷取與保存

- 後端在方向轉正、縮放、重新編碼及移除 metadata **之前**讀取 EXIF `DateTimeOriginal`、`OffsetTimeOriginal`，有完整時間及合法時區偏移才解析為 UTC。存在的小數秒可保存；缺少小數秒不影響有效性。
- 僅保存所需原始時間字串、偏移、解析後時間、解析版本與時間狀態；不保存 GPS 或整份 EXIF。重新編碼的儲存照片繼續移除 metadata。
- 不用上傳時間、檔案修改時間、EXIF 修改時間或裝置當前時區替代拍攝時間。客戶端不可提交可覆寫後端判定的拍攝時間。
- metadata 可被修改。畫面及文件稱為「照片中繼資料時間」，不得稱已驗證真實拍攝時間。帳號與照片不同也不證明不同自然人。
- 時間狀態於伺服器照片接收時判定，窗口為接收前30天至接收時刻，邊界包含；未來時間不自行容許偏移，原解析結果不改寫。自動發布前另以發布時刻檢查原回報及各支持照片是否在最近30天內；發布後因撤票或異議重算支持時，不再以照片自然老化撤銷資格。

| 時間狀態 | 意義 | 處理 |
| --- | --- | --- |
| `VALID` | 時間與偏移可解析，位於窗口內 | 可作自動補證的時間條件 |
| `MISSING` | 缺少原始拍攝時間 | 可提交，轉人工；不計自動門檻 |
| `TIMEZONE_UNKNOWN` | 有拍攝時間，缺少偏移 | 同上；不假定 Asia/Taipei |
| `INVALID` | 格式或偏移不合法、欄位矛盾 | 同上 |
| `FUTURE` | 解析時間晚於接收時間 | 同上；顯示可能裝置時間異常 |
| `OUTSIDE_WINDOW` | 超過30天 | 保留證據，不計自動門檻 |

照片解碼失敗或超過既有檔案／像素限制仍拒絕上傳，與 metadata 缺失可提交分開處理。已儲存舊照片不以 `created_at` 回填拍攝時間。

### 3.2 手機端必要調整

現有 picker 設定 `requestFullMetadata: false`、品質壓縮，可能在後端收到前就移除 EXIF。因此手機實作須讓原始／保留拍攝 metadata 的檔案到達後端，不能只新增後端解析器。

支援相機及相簿選圖，避免送出前重新編碼而丟失時間；取得 metadata 所需權限須依平台說明。選圖或裝置無法保留 metadata 時仍可提交，畫面顯示需人工核實，不繞過門檻。既有上傳大小限制維持；過大檔案提示換圖，不用遺失時間的壓縮結果冒充有效原檔。現行單張5MB上限可能使部分高像素原檔無法以有效時間提交；第1個功能 issue 須量測主要機型原檔大小，決定調整原檔上限，或在客戶端縮圖時只複製拍攝時間及偏移欄位（信任等級與原檔 EXIF 相同，仍由後端解析判定）。

## 4. 社群、初審、發布與複審

### 4.1 社群與自動發布條件

- 所有登入者都可回報、補證或提出異議，不需管理員預先授予核實資格。許可、費率及入口通行性必填車種與 zone；設備標示車種無關，仍需明確場站或區域範圍。
- 低風險限照明、遮雨、充電設備及入口位置觀察。原作者之外3個不同 `user_id`，各提供至少一張有效時間照片與自身結構化觀察，才滿足補證門檻；原回報也須有有效時間照片。無照片或缺有效時間的回報仍可進人工流程。
- 每人每案一個有效立場：「符合／不符合／無法確認」。只有符合且附獨立證據者計票；不符合須附證據才可成為有效異議。
- 同案重用 evidence ID 或正規化照片 SHA-256 不算獨立證據；此為確定性去重，不宣稱可識別所有改圖或灌票。提供頻率限制及管理員停權能力。
- 原作者不計支持票。支持者撤票、轉異議或被認定無效後，支持低於3人就暫停；發布後照片自然超過30天不追溯取消原核實，資訊維持原90天期限。
- 系統初審通過、無有效異議且達門檻，即發布「社群核實」低風險觀察，期限自首次發布時刻起90天。暫停後恢復不重設期限。到期不作現行資訊，保留歷史；續期須新案件／新版本及新的照片與補證，不重用原投票自動延長。
- 社群設備與入口獨立存為觀察，不寫入排序所用的 facilities／entrances，不影響 `sort_version=1`、`available_only`、費率篩選或預設導航。
- 許可、費率、入口通行性走第2節來源解析路徑，票數不能代替證據；可靠來源可自動確認，不必等3票。
- 空位只採可靠官方／營運商即時來源。既有 `WRONG_AVAILABILITY` 回報保留為錯誤回饋，不產生社群空位數字。

### 4.2 確定性初審與狀態

每次初審記錄規則版本、檢查代碼、結果與原因：身分／停權、欄位完整、停車區／車種、照片時間、來源適用、證據重複、有效支持、來源衝突與發布資格。不是由一個 AI 信心分數決定發布。

審查狀態與發布生命週期分開記錄，API提供下列有效狀態：

- 審查：`PRECHECK_PENDING`、`AWAITING_CORROBORATION`、`MANUAL_REVIEW`、`NEEDS_EVIDENCE`、`ACCEPTED`、`REJECTED`、`SUPERSEDED`。
- 發布：`UNPUBLISHED`、`PUBLISHED`、`SUSPENDED`、`EXPIRED`、`WITHDRAWN`。

`EXPIRED` 由目前時間與 `published_until` 在讀取時推導，不依賴背景寫入；持久化保存首次發布、暫停／撤回事件及期限。WITHDRAWN 維持撤回；其他曾發布資料到期後顯示 EXPIRED，不因原儲存值仍為 PUBLISHED／SUSPENDED 而繼續有效。

| 情況 | 審查與發布行為 |
| --- | --- |
| 必填欄位不完整 | 表單／API拒絕完成提交，指出缺欄位 |
| 低風險初審通過但支持不足 | 等待補證，未發布 |
| 低風險符合門檻 | 系統採納並發布結構化觀察 |
| 已核實來源符合明確解析規則 | 系統確認來源事實並發布 |
| 必要原回報／支持證據的時間缺失或異常、未知來源／格式、模糊內容或衝突 | 疑義轉人工，新事實未發布；額外無效照片不計票，已有足夠有效證據時不單獨阻止自動發布 |
| 已發布社群資訊出現有效異議 | 暫停該資訊，轉人工 |
| 社群資訊到期 | 已過期，原採納與歷史保留 |

有效異議須來自未停權的登入者、不是原支持的重複證據，指向同一事實／區域，附有效近期照片及不同觀察值。未通過此檢查的異議可送人工，但不能僅憑反對票自動暫停。對官方／營運商事實的異議需經來源核對；不直接全面撤回其他來源。

### 4.3 人工複審

只有疑義進入人工佇列。管理員可採納、不採納、要求補件或由新案取代，均須原因代碼及文字。補件建立新版本並重新初審，舊版本不覆寫。

採納時預覽兩車種、範圍、有效區間、發布狀態與積分影響。缺證據或最高層衝突仍不能變成已確認事實，可採納為觀察或維持未知並說明。

人工採納但未達自動社群門檻的低風險觀察，標示「人工複審採納」，不宣稱3人社群核實，期限同為首次發布起90天。人工採納缺 metadata 的照片不會把時間狀態改成 VALID，也不回填自動補證票數。

禁止審核本人提交、參與補證或提出異議的案件；保留僅供內部的不可重新指派參與者識別，以免刪除帳號使利益迴避失效。多位管理員操作用案件 `version` 檢查，版本不符回 `409 VERSION_CONFLICT`。

## 5. 貢獻、媒體與身分邊界

### 5.1 貢獻等級

- 已採納原回報或獨立補證每案每人最多1分，單純投票、待審、不採納或重複證據不給分。等級：0分新加入、1分L1、5分L2、20分L3、50分L4。
- 等級用於認可貢獻，不改票權或來源權威；3名補證者門檻不因高等級變少。
- 積分帳本只增不覆寫，以案件與使用者限制重複發放；爭議或刪照造成證據不足時凍結且不計入有效積分／等級，恢復解凍、判定無效記反向扣分。自然到期不撤回合法取得分數。
- 案件採納前提交，或有效發布期間新增且經確認有效的補證可給分，仍每案每人最多1分；到期後補證須進新一輪核實，不能向舊案件追加得分。
- 不設公開排行榜，積分／等級供本人及授權管理員查看；公開觀察顯示核實人數與時間，不公開作者或補證者身分。

### 5.2 照片與文字

首版自動公開僅結構化摘要。自由文字須人工內容審核，照片始終非公開，不承諾用確定性規則自動辨識人臉或車牌。

提交者只可透過授權媒體代理端點查看自己上傳的照片及原始 metadata 時間；他人的私人證據只有 MODERATOR 可查看。去除 metadata 的照片不暴露儲存 key，回應禁止快取。照片刪除請求由管理員處理：移除物件及私人原始時間內容，保留匿名必要審核紀錄；若因此證據不足，暫停受影響社群發布並複審。不得用備份或公開網址繼續供應已刪除媒體。

### 5.3 開發登入與發布開關

社群自動發布的功能開關預設關閉。DEV 可在隔離、限制存取的測試環境啟用，內容清楚標為測試，不能流入正式資料庫。對外公開自動發布前須完成正式身分驗證；開發登入的不同 subject 不構成防灌票能力。

本輪不做正式登入供應商接入。測試 HTTPS 通道設存取限制、獨立 DB／Redis／S3，保護 dev-session；已知限制是不同 user_id 不等於不同自然人。

## 6. 手機與獨立 Flutter Web 工作台

### 6.1 手機介面

- 停車詳情優先呈現車種適用性、入口與可靠空位，旁附各自來源、時間及新鮮度；社群觀察另區呈現，不冒充官方資料。
- 回報／補證表單含事實類型、範圍、車種、觀察值、照片／來源；上傳後顯示系統擷取的拍攝時間、時區及補證資格，不提供時間編輯欄位。缺失時顯示「可提交，需人工核實」。
- 提交前顯示提議資訊，提交後回傳案件編號。相機／相簿失敗、權限拒絕與照片過大均提供可理解訊息；照片上傳失敗不丟棄已存案件。
- 「我的貢獻」顯示本人積分、等級及案件，案件時間軸呈現初審、補證、發布、異議、補件與複審理由。待補件顯示下一步，不採納可依理由建立新版本／案件。
- 公開入口觀察標示「社群核實位置・通行性未確認」。預設導航仍優先已確認 ALLOWED 入口，無入口時明示場址定位。

### 6.2 工作台技術與畫面

- 使用獨立 Flutter Web 專案，獨立啟動／建置／部署，共用 `packages/hmp_core` 純 Dart 模型、API client 與共用驗證，不依賴手機地圖、定位、相簿或 Dynamic Color 插件。
- 採同源 API 反向代理，首版不開跨來源存取；管理員 token 僅記憶體保存，不寫 localStorage，重新整理須重新登入。測試時由 CLI 核發 MODERATOR token。
- 疑義佇列預設待複審，優先順序為已發布爭議、許可／通行性、其他，再按等待時間；篩選城市、場站、事實類型、疑義與狀態。
- 案件頁左側是場站、車種與原值／提議值，中間是私人證據與 metadata 解析結果，右側是初審檢查、衝突、發布預覽與操作，下方是不可覆寫時間軸。
- 來源連結只開允許的 HTTPS URL；證據存取同樣受後端角色及案件權限保護。採納／不採納／補件／新案取代的理由及影響在確認前可讀。
- 未登入、無權限、空佇列、缺媒體、API失敗及版本衝突都有明確畫面與重試／重新載入操作，不將失敗顯示為成功。

視覺使用既有平台與設計 tokens，套用 gpt-taste 的字體層次、留白節奏與高對比，採用 Flutter 動畫及 Reduce Motion。不引入 React／GSAP、隨機任務布局、捲動劫持或展示頁式超大留白。桌面證據並排；平板改上下排列，維持鍵盤焦點、閱讀順序與可操作目標。

## 7. API、migration 與工作拆分

API新增回報版本／補證／異議、本人案件／貢獻、初審時間軸、管理員佇列／決定及私人媒體；確切 wire schema 在第1個功能 issue 的 OpenAPI 與資料庫設計中落實。寫入使用 Bearer 身分，所有管理員操作檢查 MODERATOR，身分不接受 request body 的 user_id。

建立／補證／異議／複審使用 `Idempotency-Key`，保存24小時；同 key 不同內容回422，同內容重試回原結果。計票、發布、版本與積分在交易中一致更新。期限在讀取時判斷，不依賴尚未部署的背景排程。

migration 新增來源核實、案件版本、初審、補證、社群觀察、發布期限與積分帳本。既有報告保留原 PENDING／VERIFIED／REJECTED／SUPERSEDED 狀態及公開文字語義，不回溯發布為停車事實、不給分、不推測拍攝時間。舊 `PATCH /reports/{id}/status` 僅處理舊回報審核，不能繞過新流程發布新事實；新流程由獨立操作管理。

| 順序 | 功能 issue | 交付 |
| --- | --- | --- |
| 1 | 規格與模型 | 更新產品／API／DB文件與 ADR、狀態對照、來源配置、metadata／初審契約及 migration |
| 2 | 雙北資料 | 官方字典、路邊範圍、場站對應、營運商來源核實及真實 fixture |
| 3 | 社群後端 | 初審、補證、發布／異議／複審、積分及預設關閉開關 |
| 4 | 手機 | 共用 Dart package、metadata 保留、回報／補證／貢獻與找位資訊 |
| 5 | Web工作台 | 獨立 Flutter 專案、同源代理、私人證據與疑義操作 |
| 6 | 整合驗收 | 隔離環境、HTTPS、資料重播、實機操作及阻塞修復 |

每個功能 issue 建立時更新文件追蹤連結；此文件 issue 不冒充以上六項已完成，不一次建立所有功能 PR。

## 8. 驗證、Claude 審查處理與結案

### 8.1 必驗案例

- 規則：同層 NULL／已知衝突、區域優先全場、普重／大重差異與 LIGHT_MOTO_ONLY；來源撤回、有效區間、首次範圍時間及共享空位不重複。

- UX：定位拒絕、目的地搜尋、各事實來源、入口導航、收藏／回報、深淺色、最大字體、VoiceOver／TalkBack，Web桌面／平板／鍵盤與減少動態。

功能變更通過 backend lint、pytest、migration；手機與工作台 `flutter analyze`／`flutter test`、`flutter build web`；Docker／Compose及 CI Android APK、iOS simulator 建置。自動測試不能代替 iPhone／Android 實機驗收。
